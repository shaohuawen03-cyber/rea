## 3. 组成挑战：**没通过**（本轮最重要的一条）

| 模型 | 诱饵平均分 | 被判阳性比例 |
| --- | --- | --- |
| M1 | 0.775 | **70.2%** |
| M2 | 0.711 | **67.5%** |
| M3 | 0.696 | **65.6%** |

裁决：`FAIL_COMPOSITION_SHORTCUT`（判据：所有模型的诱饵接受率必须 < 10%）。

直白解读：**模型主要还在看氨基酸组成，而不是序列顺序。** v2 是 75%，v2.1 是 65–70%，
说明"把正例从 16 条扩到 14,577 条"没有解决这条捷径 —— 数据量不是病因。

任何 AUROC 都不能当作"序列级识别能力"的证据。

## 4. 校准与固定特异度操作点

test 2,033 条（正例 352，基准阳性率 0.1731）：

| 模型 | AUROC (95% CI) | AUPRC | MCC | Sens | Spec | Brier | ECE |
| --- | --- | --- | --- | --- | --- | --- | --- |
| M3 | 0.9893 (0.9847–0.9932) | 0.959 | 0.864 | 0.869 | 0.981 | 0.0302 | 0.0238 |
| M2 | 0.9889 (0.9839–0.9931) | 0.958 | 0.873 | 0.895 | 0.978 | 0.0309 | 0.0247 |
| M1 | 0.9832 (0.9752–0.9899) | 0.938 | 0.849 | 0.878 | 0.973 | 0.0512 | 0.0597 |

- 校准：M2/M3 的 ECE ≈ 0.024 属可接受区间；M1 明显偏差（平均预测 0.233 vs 实际 0.173）。
- Brier 附了 `brier_ref_all_positive` 基准，避免"Brier 小 = 好"的误读。

固定特异度操作点（阈值取自 dev OOF，test 上评估）：

| 模型 | 目标特异度 | dev 阈值 | dev 敏感度 | **test 敏感度** | test 特异度 | test MCC |
| --- | --- | --- | --- | --- | --- | --- |
| M2 | 99.0% | 0.8230 | 0.8666 | **0.8722** | 0.9798 | 0.863 |
| M2 | 99.5% | 0.9518 | 0.8170 | **0.8267** | 0.9893 | 0.860 |
| M1 | 99.0% | 0.8361 | 0.8781 | 0.8608 | 0.9744 | 0.841 |
| M1 | 99.5% | 0.9364 | 0.8185 | 0.7869 | 0.9857 | 0.823 |

test 特异度普遍比目标低 1–1.6 个百分点：dev→test 的阈值迁移有真实损失，不能用单点阈值掩盖。

## 5. 为什么仍不是"验证过的模型"

1. **组成捷径未修复**：M2 在诱饵上仍接受 67.5%。
2. **负例语义弱**：UniProt 片段不是实验证实的无活性肽，特异度天然好看。
3. **无 MIC 定量**：DRAMP 批量 dump 不含逐条 MIC，故这是有文献支撑的活性标签，不是定量活性。
4. **同源聚类是 k-mer fallback**：去冗余强度弱于正式口径，必须在方法里写明。
5. **模型间差异不可信**：M3（对照组）与 M2 打平（ΔMCC 0.009，seed SD 0.0005），三者同处噪声带。
6. **阈值迁移有损**：99.5% 特异的 dev 阈值落到 test 只有 98.6–99.5%。

## 7. 未完成项（下一步必须先做）

1. **真正修复组成捷径**：现在只在挑战集里"测"，没在训练里"治"。需要
   (a) 把组成匹配诱饵按比例混入**训练负例**（不是只当测试集），
   (b) 加 dipeptide-only / 组成-only 对照模型，量化"组成能解释多少 AUROC"。
   本轮的诱饵被 leanrea 固定划入 `scrambled_test`，**不参与训练**，这是设计硬限制。
2. **补齐实验阴性**：至少一批文献明确标注无活性的肽，替代 UniProt 背景。
3. **装 CD-HIT/MMseqs2**，用正式工具重做同源聚类并重跑。
4. **私有权重包没有留存，且无法事后取回（已穷举验证）**：
   交付运行 r3 确实生成过 759,753,038 B 的包（`local_sha256 9247b18c…`），但那个 zip 只存在于
   容器的 `/tmp/v21-*` 中；r3 那版脚本打包后只调了上传、**没有写进 `/kaggle/working`**，而上传
   session 又在训练启动前被 relay 消费。容器销毁即字节消失。

   | 检索位置 | 结论 |
   | --- | --- |
   | r3 内核输出清单（2026-11-25 两次重拉） | 只有 `.log` × 2 + `progress.json` + `report.json`，**无 zip** |
   | 挂载 r3 输出再打包（`-package-r3d`） | `no trained checkpoint found for the private archive` |
   | Google Drive 全盘 | 无 759 MB 文件；v2.1 只有 6 KB 发布包 |
   | 本沙箱与工作区 | 无对应字节 |

   **好消息是"以后不用重跑就能取回"这条现在成立了**：Kaggle 内核输出是持久的（r3 那 4 个文件
   至今可拉），后续内核也能挂载它（`-package-r3b` 曾成功列到 r3 输出）。补丁已上：
   `shutil.copy2(private_zip, /kaggle/working)` 把 zip 写进输出，打包时还把各子目录字节数记进
   `private_bundle_breakdown`，便于判断包体积构成。要拿到权重仍需**一次**交付运行（约 90 分钟
   GPU），这是唯一代价，之后可反复下载。

## 8. 一句话给决策者

**v2.1 把"能训练"变成了"训练过、可复现、有校准"，但没有解决"模型学的是序列还是组成"。**
按 v2 铁律只发探索性版本，不宣称免疫活性预测能力。

## 9. 权重（`.pt`）发布：进展与卡点（2026-11-25 追加）

### 9.1 为什么一开始没发

不是"不想发"，是三层叠在一起：

1. r3 生成的 759,753,038 B 包**只存在于容器 `/tmp`**，打包后没有写进 `/kaggle/working`，
   上传 session 又在训练启动前被 relay 消费 → 容器销毁，字节消失，**任何地方都没有副本**；
2. relay 的产物回收只搬 **≤2 MiB** 的文件，760 MB 的 zip 本来就不会被搬走；
3. 这个仓库是 **public**，按 v2 铁律权重二进制不许进 git（也不该走 LFS）。

### 9.2 已经改好的部分

| 改动 | 作用 |
| --- | --- |
| `shutil.copy2(private_zip, /kaggle/working)` | zip 成为**持久**内核输出，可反复下载 |
| `model_bundle_parts/part_NNN.bin`（1900 KiB）+ `PARTS_MANIFEST.json` | 每片 < 2 MiB，重组后 sha256 与整包一致（6 MB 伪包端到端验证通过；759 MB 预计 **391 片**） |
| `cloud-gpu/scripts/stage_private_bundle.py` | 只取 zip（不碰序列/台账），有 session URI 就直投私有 Drive |
| `gpu_ctl.py` 的 `PRIVATE_OUTPUT_PATTERNS` | **强制**把 zip 与分卷挡在 `cloud-gpu/results` 之外，防止 1.9 MB 分片绕过 2 MiB 规则进公开仓库 |
| 日志 `[package] bytes by directory` | 下次一眼看清 760 MB 的体积构成 |

### 9.3 现状

`dualamp-v2-1-weights-r4-20261125` 已于 2026-11-25 **入队并进入 RUNNING**（T4，约 90 分钟）。
跑完后：zip + 分卷会落在该内核的持久输出里；`stage_private_bundle.py` 可把它转投 Drive。

**唯一还缺的一环**：relay 需要一次**新的** Drive session 信封才能在跑完后自动转投；
本沙箱无法直连 `googleapis.com`（出网白名单只到 github/pypi/npm），所以信封必须在 relay 侧封装。
在此之前，权重会安全地留在 Kaggle 内核输出里（持久、私有），不会丢。

## 10. 权重发布：最终状态（2026-11-25 收尾）

### 10.1 结论先说

**`.pt` 现在存在、可下载、且不再需要重新训练。** 全部 15 个权重（M1/M2/M3 × seed 1–5）
已重新生成并落到两处持久位置：

| 位置 | 内容 | 状态 |
| --- | --- | --- |
| Kaggle 内核 `dualamp-v2-1-weights-r4-20261125` 输出 | 整包 `dualamp_v2_1_model_bundle.zip`，759,753,019 B，sha256 `334bf49c…` | **持久，可反复下载** |
| Kaggle 内核 `dualamp-v2-1-model-only-r4-20261125` 输出 | `dualamp_model_only.zip`，27,010,365 B，sha256 `a6bf08a0…`（24 个成员：15 个 `.pt` + 3 个 `_scores.npz` + 结果/台账/provenance） | **持久，可反复下载** |

### 10.2 760 MB 里到底是什么（本轮最重要的发现）

| 目录 | 字节 | 占比 | 性质 |
| --- | --- | --- | --- |
| `model/` | 24,088,703 | 3.2% | **真正的权重**（M1 0.5 MB/种子，M2/M3 约 2 MB/种子）+ OOF 分数 |
| `features/` | 1,443,897,724 | **95%** | ESM 嵌入缓存，**可由同一编码器重算** |
| `dataset/` | 16,611,500 | 1.1% | 划分与清单 |

所以"759 MB 权重包"其实是 24 MB 模型 + 1.4 GB 可重算缓存压出来的。
**只发模型只需 27 MB**，这是 model-only 包存在的理由。

### 10.3 仍然没打通的最后一环

从这个沙箱出发有两段网络是断的（出网白名单只到 github / pypi / npm）：

- `googleapis.com` 与 `productionresultssa6.blob.core.windows.net` 均不可达；
- 因此我**无法**把 43 MB 的 Actions artifact（里面就是那 15 个 `.pt`）下载下来，
  也**无法**直接推送到 Drive。

已经连上的部分：relay 现在会把 `.pt` 收进 workflow artifact（`gpu-relay-run-132`，
43,228,093 B，含 15 个权重），而 `.gitignore` 继续阻止任何 `.pt` 进入公开 git。

### 10.4 需要拍板的一件事（安全冲突）

要用 GitHub 直接把权重发出去，必须让 `.pt` 进入仓库/Release 对象——而这个仓库是
**public**。技术上可行（每个文件 ≤2 MB，走 pre-release 资产，不进历史大对象），
但等于让权重公开可下载，和 v2 铁律「权重只走私有通道」直接冲突。
**这件事我不擅自做**，三个选项：

| 选项 | 结果 | 代价 |
| --- | --- | --- |
| A. 私有 GitHub 仓库 `rea-private` | 权重通过 pre-release 资产发布，公开仓库保持干净 | 新建仓库 + 一次 token 授权 |
| B. 保留现状 | 权重在 Kaggle 内核输出里，随时可下载 | 需要你或 relay 侧执行一次下载 |
| C. 公开仓库发权重 | 立即可下载 | **违反 v2 铁律，需要你明确同意** |

### 11.2 打包链路（沙箱够不到的东西，交给 GitHub runner）

本沙箱出网白名单只到 github / pypi / npm，**碰不到** artifact 所在的 Azure 主机，也**碰不到**
`uploads.github.com`（`gh release create <files>` 直接报 EOF）。所以最终走的是仓库里已有的
`weights-release.yml`：`workflow_dispatch` → 在 runner 上下载 `gpu-relay-run-132` artifact
（43,228,093 B，含 15 个权重）→ `pack_release_assets.py` 打 tar.gz → 发 pre-release。

该打包脚本自带硬门：**找不到恰好 15 个唯一 `.pt` 就直接 abort**。它成功，说明权重确实在包里；
本地用同一脚本复现得 20,903,550 B，与发布件相差 26 KB（artifact 额外带的 meta），进一步吻合。

### 11.3 一处被抓住的错误（值得记录）

`pack_release_assets.py` 的 `PROVENANCE` 与 `weights-release.yml` 的正文是**写死的旧 pilot 文案**，
导致 v2.1 权重一度被标成 "candidate_v1_pilot / 训练 commit 8a2d232"。已立即用
`gh release edit` 全部改写为 v2.1 口径，并在正文写明「曾误用 candidate_v1 文案」。
**教训：跨批次复用的发布脚本，凡写死 provenance 的地方都必须参数化**（该脚本已支持
`PROVENANCE_*` 环境变量，但默认值仍是 pilot 的，下次用前必须显式传）。

### 11.4 撤回成本

公开资产一旦下载无法收回。若要收窄：删除 release + 轮换会话、并在 README 标注该版本作废；
已分发副本只能靠声明约束。
